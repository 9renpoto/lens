# v0.2 task breakdown

This is the current local planning revision based on ADRs 0004–0007. Linked GitHub issues may describe earlier scope until explicitly updated; obsolete local issue-body copies have been removed. Their existing completion states do not establish completion of the revised work. This document does not create, reopen or update GitHub issues.

## Work boundaries

| Task | Work to deliver | Prerequisites |
| --- | --- | --- |
| A. Register targets and sources | API to register/change companies and source routes; remove fixed issuer restrictions from code and database; document registration without prescribing company names | ADR 0007; decide registration fields and validation |
| B. Store PDFs in RustFS | RustFS deployment/connection; stable content-based file locations; exact PDF retrieval; keep domain records in PostgreSQL | ADR 0005 |
| C. Recover interrupted storage | Durable work records before writes; repeat-safe recovery; bounded automatic retries; manual recovery and visible unfinished work | B; ADR 0006; decide retry count and spacing |
| D. Move existing retained PDFs | Transfer existing PostgreSQL originals without losing file identity, acquisition history or extraction links; verify contents before switching reads; define rollback | B, C; agree migration procedure |
| E. Connect collection and text processing | Use registered routes and RustFS-backed originals for bounded collection and reprocessing | A, B, C; settle collection, identity and processing decisions |
| F. Complete search and operator access | Search and inspect originals, history and failures; operator identity confirmation | E; settle selection/search/API contracts |
| G. Verify deployment and recovery | Use local k3s Lens; back up and restore PostgreSQL and RustFS as one recovery point; reconcile every completed object reference and content hash after restore; repair from the coordinated backup when possible; mark an unrecoverable original unavailable and surface it to the operator | A–F; agree backup and verification scenarios |

A and B can be developed independently. C follows B; D and E follow the recovery foundation. F follows E. G verifies the complete agreed flow, including migration where existing data is present. This ordering is a planning dependency, not a new GitHub dependency registration.

The fixed-issuer removal affects `SourceCatalog`, `Identity`, `HTTPCheck` and the database issuer-code constraint. Change an existing database through a forward migration rather than rewriting a previously applied migration. Preserve historical records. Keep deterministic tests and TDD for production changes.

# v0.2のタスク分解

ADR 0004〜0007に基づく、現在のローカル計画更新。リンク先のGitHub Issueは明示的に更新するまで以前の範囲を記述している場合がある。古いローカルのIssue本文コピーは削除した。既存の完了状態は、見直した作業の完了を意味しない。この文書ではGitHub Issueの作成・再オープン・更新は行わない。

## 作業の境界

| タスク | 実現する内容 | 前提 |
| --- | --- | --- |
| A. 対象・取得先の登録 | 企業と取得経路を登録・変更するAPI。コードとDBの固定企業制限を除去。企業名を運用方針として指定せず登録方法を説明 | ADR 0007。登録項目と検証規則の決定 |
| B. RustFSへのPDF保存 | RustFSの配置・接続。内容に基づく固定保存先。正確なPDF取得。資料の関連記録はPostgreSQLに保持 | ADR 0005 |
| C. 中断した保存の復旧 | 書き込み前の永続的な作業記録。繰り返しても安全な復旧。回数制限付き自動再試行。手動復旧と未完了作業の参照 | B、ADR 0006。再試行回数・間隔の決定 |
| D. 既存PDFの移行 | PostgreSQLの既存原本を、識別・取得履歴・抽出との対応を失わず移す。読み取り先切替前に内容を確認。戻し方を定義 | B、C。移行手順の合意 |
| E. 収集・本文処理への接続 | 登録した経路とRustFS原本を使う、上限付き収集と再処理 | A、B、C。収集・識別・本文処理の判断 |
| F. 検索・運用者向け操作の完成 | 検索、原本・履歴・失敗の参照、運用者による識別確定 | E。選択・検索・APIの契約 |
| G. 実環境・復旧の検証 | ローカルk3s上のLensで登録・収集・保存・再処理・検索を検証。PostgreSQLとRustFSを一つの復旧時点としてバックアップ・復元する。復元後に完了済みファイルの参照先と内容ハッシュを照合し、可能なら同じバックアップから修復する。有効な原本を復元できない場合は利用不可として運用者に示す | A〜F。バックアップと検証シナリオの合意 |

AとBは独立して進められる。CはBに続き、DとEは復旧基盤に続く。FはEに続く。Gは、既存データがある場合の移行も含め、合意した一連の動作を検証する。これは計画上の依存関係であり、GitHubへ新しい依存関係を登録したものではない。

固定企業制限の除去は、`SourceCatalog`、`Identity`、`HTTPCheck`とDBの企業コード制約に影響する。適用済みのマイグレーションを書き換えず、新しいマイグレーションで既存DBを変更する。過去の記録を維持する。本番変更は再現可能なテストとTDDで進める。
